ARCHITECTURE 01 / SLIDING WINDOW

SWA：把可见历史压到一条窗口边界

SWA 让每个 token 只回看最近 W 个 token。但前缀复用、投机解码与 chunked prefill 都要求多留一段窗口外余量，于是“窗口 + 额外保留”成为 SWA cache 的基本尺寸。

ENGINE 01 / PAGED ATTENTION

vLLM

不新增 cache 类型：把 SWA 当作带窗口约束的 full-attention 变体。

存储层沿用 full-attention 的分页块体系。SWA 的改变不在“有没有 block table”， 而在 SWA group 的逻辑块大小，以及每个请求需要多保留一段窗口外 token。

每个请求的保留量由一个线性式给出：窗口长度减一，再加上额外保留。worker 会把完全低于该 token 数的 block-table 项整体置空——注意是置空表项，而不是拆掉块结构。

前缀缓存的判断也因此改变。manager 不再只做一次最长公共前缀比较，而是从当前候选命中长度出发， 自右向左按粒度比较 window 是否命中；一旦某一段不命中，就退到下一个候选命中长度位置重新试探。

驱逐同时受两条规则约束：窗外与 LRU。前者是硬边界，后者决定边界内谁先走。

KEY RULE

保留阈值 = sliding_window − 1 + extra_retained_tokens；阈值以下的 block-table 项置空， 前缀匹配按窗口粒度回退。

RETENTION / vLLM
num_retained_tokens =
  sliding_window − 1
  + extra_retained_tokens

低于该值的 block-table 项被 worker 置空；窗口外并非立即物理释放，而是先失去可读性。

ENGINE 02 / UNIFIED RADIX CACHE

SGLang

同一棵前缀树，多挂一个 SWA component。

SGLang 用 Unified Radix Cache 统一管理 full-attention 与 SWA。基础存储仍按前缀树组织， 区别是每个节点额外挂一个 SWA component，维护该节点对应的窗口缓冲。

组件承担匹配、插入、恢复、驱逐四类操作。笔记对“恢复”没有展开，但其余三条给出了足够清晰的规则。

01

匹配

以累计长度定位窗口边界；遇到 tombstone 归零，重新开窗。

02

插入

沿用正常 kv_cache 插入方式，在节点上附加 SWA 缓冲。

03

恢复

从缺失或 tombstone 状态恢复窗口缓冲；细节未展开。

04

驱逐

独立 LRU + 窗口；叶子直接删，中间节点留 tombstone。

驱逐分两种情况：叶子节点直接删除；中间节点不能删结构，于是把 SWA 对应的 value 置为 None，留下一个 tombstone。前缀树因此保持完整，但该节点不再提供可用的窗口状态。

匹配从根开始累计长度，初值取正无穷；累计长度超过窗口长度时记为匹配边界。遇到 tombstone， 累计长度归零，相当于从该节点之后重新开窗，最终取能够成立的最佳边界。

MATCH / 累计长度
c = +∞
if c > window → boundary
if tombstone → c = 0

从根向叶推进；tombstone 是窗口预算的重置点，而不是树的断点。

ENGINE 03 / TWO-TIER KV

DeepInfer

把 SWA cache 放到本机内存，把 Block KVCache 留在 3FS。

DeepInfer 是三者中唯一明确区分 SWA cache 物理位置的实现：Block KVCache 存在 3FS 集群， 按 128 token 分页，存放 4 层 main KV 与 indexer K；SWA KVCache 存在本机内存， 前 20 层各一个 134 token 的 ring。

134 = 128 窗口 + 6 投机回退。ring 不保存压缩中间态，意味着它只维护窗口内可计算的 K/V 状态， 而不承担额外的压缩缓存。

写入时机被严格约束：prefill 之后写入的位置取“序列末尾留出一个 token 后、向下对齐到 128”； 不足 128 tokens 则本轮不存；chunked prefill 中途不存，只有最后一个 chunk 才存； decode 阶段在副本最近一次拷贝的位置存。

匹配基准

以 Block KVCache 为基准（假设命中 L1），只考虑两种情形：L1——128 token 窗口可复用； L1 − 128——窗口需要重算。

STORAGE SPLIT

窗口长度 128；投机回退预留 6 个 token。

01 / PREFILL

prefill 之后

位置取“序列末尾留出 1 token 后向下对齐到 128”；不足 128 tokens 则本轮不存。

02 / CHUNKED

chunked prefill

中途不存，只有最后一个 chunk 才写 SWA KVCache；避免为未完成的窗口反复落状态。

03 / DECODE

decode

在副本最近一次拷贝的位置存储，跟随 decode 期间的状态副本推进。

ENCODER

补窗口，不动 Block

SWA KVCache 缺失时，重算命中前缀的最后 128 个 token，与未命中后缀一同前向；重算段只重建 SWA KVCache，Block KVCache 原样复用。

DECODER

把精确重建变成有界重放

CED 架构下 decoder 的 Block KVCache 由 encoder 末层 hidden state 投影得到；仅 decoder SWA KVCache 需各层自算。精确重建要跑 2560 个 token，改为每次 prompt 末尾 128 个。

要点 01

抽象不变，边界外置

三家都保留 full-attention 的块 / 树抽象，SWA 只在其上增加一条“窗口边界”。

要点 02

三种“窗外”写法

vLLM 用阈值置空，SGLang 用 tombstone，DeepInfer 用两层存储；本质都是把窗外变成可管理的状态。

要点 03

匹配问题变了

前缀复用的难点从“找相同前缀”转为“判断窗口是否仍然有效”。

ARCHITECTURE 02 / DEEPSEEK SPARSE ATTENTION

DSA：把“看哪些历史”交给一个索引器

DSA 在主注意力之外增加 indexer：先对历史 token 选 top-k，再让主注意力只在这些 token 上计算。 cache 因此拆成 Indexer K Cache 与 MLA KV Cache 两套。

ENGINE 01 / TWO CACHE PLANES

vLLM

结构可确认，规则未公开。

vLLM 为 DSA 分配两块存储：Indexer K Cache 缓存历史 K，MLA KV Cache 承载主 attention 的 kv_cache。两者按 block 组织，附图中的 layerN.indexer 与 layerN.mla 共享同一组 block_id。

但在 DeepSeek V3.2、V4、V4.1 的 vLLM 官方博客里，都没有找到这两套 cache 在前缀缓存、 驱逐与匹配上的专门说明。GLM 5.3 的 HiSparse 驻留优化是另一条线索：它讨论的是驻留策略， 不是 cache 生命周期，因此同样没有给出匹配 / 驱逐规则。

资料缺口

当前能确认的是“有两套、按 block 对齐、indexer 为主注意力选路”； 两套缓存如何联合做前缀匹配、驱逐是否同步，仍是空白。

ENGINE 02 / INDEX-K CACHE

SGLang

单独维护 Index-K，并做 Kpool + tail 压缩。

SGLang 与 vLLM 同构：单独维护 Index-K cache，并对 Index 做压缩优化（Kpool + tail）。 其余逻辑与 full-attention 处理类似。

一个值得注意的实现细节是：/unified_cache 目录下的 component_type.py 中没有为 DSA 维护的 component 类型。这说明统一 cache 抽象还没有把 DSA 当成独立类型，实际路径更可能复用 full-attention 的组件。

因此，SGLang 的 DSA cache 更像是“两套存储 + 一套通用管理”，而不是像 SWA 那样 拥有专门的 component。

要点 01

核心是“两套状态”

DSA 的 cache 问题不是单套 KV 的窗口边界，而是 indexer K 与 MLA KV 的一致性。

要点 02

公开资料停在结构层

两家都能确认双缓存与 block 对齐，但联合驱逐与联合前缀匹配仍是空白。

要点 03

驻留是另一个维度

HiSparse 提示：cache 放在哪里，可以与 cache 何时失效分开讨论。

ARCHITECTURE 03 / MINIMAX SPARSE ATTENTION

MSA：存储不动，把稀疏性留给计算

MSA 采用 Standard Storage, Sparse Computation：KV 仍按标准方式分配和保留， 稀疏性体现在计算时选择哪些块参与。

ENGINE 01 / STANDARD STORAGE

vLLM

标准存储 + 稀疏计算；先验证交互，再启用前缀缓存。

从 vLLM 关于 MiniMax M3 的文档可以确认：MSA 的 kv_cache 采用标准存储设计，配合稀疏运算。 缓存分配沿用基础存储，计算时再应用稀疏性。

为了适配运算，实现需要显式跟踪主 kv_cache 与 indexer K cache。只有当两套缓存之间的交互 验证正确后，prefix cache 与 chunk fill 才可以启用。

关键条件

这条规则很重要：MSA 不是“因为标准存储就自动获得前缀缓存”，而是“标准存储提供了复用基础， 交互验证决定能否启用”。

ENGINE 02 / RADIX + INDEX-K

SGLang

主缓存走 radix，索引缓存单独维护。

从 SGLang 开源代码看，MSA 的处理与 vLLM 类似：主缓存沿用 radix tree 体系，复用与驱逐单独计算； 另外维护一个 index K cache，用于计算主缓存中的历史 block。

换句话说，radix 负责“主 KV 怎么复用”，index K 负责“稀疏选择看哪些历史”， 两者在计算路径上汇合。
