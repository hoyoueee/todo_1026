SWA

vllm

存储上保留和full-attention一样的模式，区别在于对于SWA的group中的逻辑块（block）大小与full-attention group的存在差异，整体存放的大小包括窗口大小与额外保留大小

def num_retained_tokens(self) -> int:
        """Tokens below a request's first scheduled position that must stay
        readable. The worker nulls a step's block-table entries wholly below
        that many tokens.
        """
        return self.sliding_window - 1 + self.extra_retained_tokens

在进行前缀缓存的判断时，manager根据当前候选命中长度，从右至左依次按粒度比较window是否命中，存在未命中则退至下一个候选命中长度位置。

例如：

缓存命中前缀可能有 3 种：

  • 缓存命中长度为 5，计算预填充 [2, 3, 4] → [5, 6, …, 14]
  • 缓存命中长度为 6，计算预填充为 [3, 4, 5] → [6, 7, …, 14]
  • 缓存命中长度为 14，使用 [11, 12, 13] → [14] 进行预填充（效率最高）

驱逐方面采用窗外 + LRU两种模式同时进行，一方面对保留大小外的块进行驱逐，另外配合LRU的策略。

SGLang

sglang采取的是Unified Radix Cache的存储模式，在cache的基本存储上同样与full-attention的情况相同，同一结点由SWA component维护SWA的缓冲数据，期间涉及的操作包括匹配、插入、恢复、驱逐

  • 驱逐 SWA component 根据其独立的LRU以及窗口大小进行驱逐，对于要驱逐的叶子结点，直接删除，对于中间结点则将SWA对应的结点value置为none，记为tombstone
  • 匹配 SWA的匹配依赖于“累计长度”，从根节点开始，累计长度设为正无穷，对于任意结点，如果累计长度大于窗口长度，记为匹配边界。当遇到SWA无效节点（tombstone）累计长度归0，就这样找到最佳匹配边界
  • 插入 保留正常的kv_cache插入方式。

在存储方面，将SWA KVCache进行了区分

SWA 对应的缓存会在prefill之后再存储：位置取序列末尾留出一个 token 后向下对齐到 128 所得的位置，不足一个 128 tokens 则本轮不存储；chunked prefill 中途不存储，只有最后一个 chunk 才存储 ；decode阶段 会在副本去最近一次拷贝的位置存储。

在匹配时，以Block KVCache为基准（假设命中L1)，只考虑L1（128token窗口可复用)、L1-128（窗口重算)两种情况。

MSA

vLLM

通过vLLM关于MiniMax M3的文档，可以了解到MSA的kv_cache为 标准的存储设计 配合 稀疏运算（Standard Storage, Sparse Computation）具体来说在缓存分配上是沿用基础存储，在计算时应用稀疏性，但是为了适配运算，需要显示的跟踪主kv_cache, indexer K cache，当缓存之间的交互验证正确后，可以适用prefix cache和chunk fill。

SGLang

通过对sglang开源代码的分析，了解到对MSA的处理与vLLM类似，sglang将MSA主缓存沿用radix tree体系，单独计算复用与驱逐，另外维护一个index K cache，用于计算主缓存中的历史block

存储模式

main：GQA K/V

main_pool · page_size=128
K · 1,024 B V · 1,024 B
4 KV head × 256 dim（K+V）× 2 B（bf16）= 2,048 B/token。
page：128 × 2,048 = 256 KiB

index：index_k_pool

key-only · 每层一份 · page_size=128
index K · 256 B
1 个 head × 128 dim × 2 B（bf16）= 256 B/token。
page：128 × 256 = 32 KiB
一个 page 的合计：256 KiB + 32 KiB = 288 KiB；每 token 2,048 + 256 = 2,304 B。
